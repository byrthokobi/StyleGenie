# ADR-002: Dual ID Strategy — BIGSERIAL Primary Key + UUID Public Identifier

## Context

Every entity in StyleGenie needs a primary key for internal database operations (foreign keys, joins, indexing) and an identifier to expose in API responses. Two common strategies exist: UUID-as-PK (single field, same value internal and external) or a dual-ID approach (auto-increment integer PK internally, UUID for the public API surface).

The `users` table is the most critical — all other tables will foreign-key into it, and the user identifier will appear in JWT claims and API responses.

## Decision

Use **BIGSERIAL** (`id`) as the actual database PRIMARY KEY for internal use, plus a **UUID** (`public_id`) as the externally exposed identifier on all entities. Foreign keys between tables always reference the `BIGSERIAL id`, not the UUID.

## Rationale

UUID v4 values are random. Using them as a clustered primary key causes B-tree index fragmentation in PostgreSQL because each new row inserts into a random position in the index rather than appending to the end. On high-write tables, this causes page splits and index bloat over time.

BIGSERIAL is sequential — new rows always append to the end of the index, which is optimal for PostgreSQL's B-tree. Foreign key joins on a BIGINT are also cheaper than UUID joins (8 bytes vs 16 bytes, native integer comparison).

The UUID is still needed externally to prevent sequential ID enumeration (an attacker cannot guess `?userId=1001` if the public API only ever shows UUIDs).

### Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|--------------|
| UUID-as-PK only | Single field, simple | Random inserts → B-tree fragmentation; 16-byte FK joins; sequential enumeration risk exists if UUID is predictable | Index fragmentation is a real concern at scale |
| BIGSERIAL-as-PK only (expose integer) | Best DB performance | Integer IDs in API allow sequential enumeration of users — security risk | Enumeration is a meaningful risk for a user-facing app |
| BIGSERIAL + UUID (chosen) | Fast internal joins and indexing; safe external exposure | Two ID fields per table; slightly more complex JPA mapping | Accepted trade-off — complexity is low, benefits are concrete |
| UUID v7 (time-ordered) as PK | Sequential, no fragmentation, single field | Not natively supported in PostgreSQL < 17; requires extension or app-side generation; team unfamiliarity | Deferred — revisit when PostgreSQL 17 support is confirmed |

## Consequences

### Positive

- Optimal B-tree performance — sequential BIGSERIAL inserts, no fragmentation.
- Cheap 8-byte BIGINT foreign key joins across all tables.
- No user/entity enumeration via public API — only UUIDs are exposed.
- `public_id` generated by PostgreSQL (`DEFAULT gen_random_uuid()`) — no application-side UUID generation needed.

### Negative

- Two ID fields on every entity — JPA entity class needs both `@Id Long id` and `UUID publicId`.
- DTOs must explicitly map `publicId` (not `id`) — discipline required to never leak `id` in responses.

### Risks

- **Accidental `id` exposure**: If a developer adds `id` to a DTO or logs it, the internal integer is exposed. Mitigated by code review conventions: all response DTOs reference `publicId` only; `id` is package-private or never mapped to a response DTO.
